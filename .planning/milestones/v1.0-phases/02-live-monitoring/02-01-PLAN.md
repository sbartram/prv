# Phase 02 Plan 01: Tracer — prv refreshes itself on the config interval, and a failed refresh never hides the data on screen

## Phase Goal

**As a** developer who keeps prv open in a terminal pane all day, **I want to** have it refresh itself, stay inside the API rate limit, narrow the list and jump to a PR on github.com, **so that** I can trust that what I see is current without opening a browser.

(Derived from the ROADMAP Phase 2 Goal line, which is not written in user-story form; see the planner's return note.)

<objective>
Prove the refresh architecture end-to-end first, then make a failure safe.

- Task 1 (tracer): `refresh_interval` in `config.toml` → `cmd/prv` → `ui.Options.Interval` → one generation-stamped tick chain → `Fetcher.Fetch` (the real github client in the end-to-end test) → the model records the time of the last successful fetch.
- Task 2: a failed refresh keeps the rows on screen (D-07: not dimmed, no error panel), a failed first fetch keeps the Phase 1 panel and retries on its own (D-09), and a result from an older generation is dropped.

Purpose: success criterion 1 (interval from config, defaults without a config file) and the "last data stays on screen" part of success criterion 2. Decisions D-07 (rows kept and not dimmed), D-09 (automatic retry of the first fetch), D-14 (refresh_interval), D-15 (exit 2 on a value that cannot be parsed). Roadmap pitfalls: single-flight, one tick chain, generation counter, panic-safe Cmds, cancel on quit.
Output: `internal/config`, `internal/ui/refresh.go`, the refresh state machine in `internal/ui/model.go`.

Later plans in this phase build on this slice: 02-02 (r from every screen, "updated HH:MM:SS", selection by ref), 02-04 (failure marker, "retrying at").
</objective>
