# Phase 03 Plan 11: Each partial-read cause gets its own honest text in the detail view (gap G-03-6, review WR-05)

## Phase Goal

**As a** prv user watching my pull requests, **I want to** see without leaving the terminal who and what is holding each PR up (which reviewers, which failing check, and whether it can merge), **so that** at a glance I can tell which watched PRs are approved, blocked, or failing CI.

<objective>
Close UAT gap G-03-6 (code-review finding WR-05). On 2026-10-12 the user chose "fix before ship".

Plan 03-09 gave `domain.Detail.Truncated` two meanings. One is "fewer check runs were read than exist". The other is "GitHub kept a GraphQL error next to the data, so a check, reviewer or review request may be missing". The only renderer, `checksSummary`, turns both into `read <Read> of <Total> runs`. That causes two wrong outputs:
1. A kept error about a reviewer, with every run read, shows "read 3 of 3 runs". This looks complete, but the reviewer list may be missing people.
2. A PR with no statusCheckRollup plus a kept error on page 1 shows "CHECKS  read 0 of 0 runs" instead of "CHECKS  no checks".

The fix splits the signal. `Truncated` keeps one meaning: check runs were not read. A new `Partial` flag means a GraphQL error was kept next to the data. Each flag gets its own text.

- Task 1 (tracer): add `Detail.Partial`. FetchDetail sets it instead of Truncated, and the detail view shows a faint "some details could not be loaded" line under the title. Both WR-05 cases are proven end to end, through the real github.Client and the real ui.Model, with tests written first.
- Task 2: rendered-output tests at the ui.Model level for every Truncated/Partial combination, as the review asked. Also a `detail-partial` golden set at 0x0, 60x15, 80x24 and 120x40, which follows the 03-08 rule that every detail state has goldens (D-14).

Purpose: the detail view must not use "complete" words for a partial read. Only that cause changes. D-03 and D-08 ("keep the exact counts and say how much was read") stay as they are: "read N of M runs" still shows when runs were not read.
Output: a `Partial` field, one changed line in FetchDetail, one new note in detailNotes, tests, and 4 new golden files.

Claude's discretion (recorded): the notice goes in `detailNotes`, on its own faint line under the title. That is the line where the faint "no longer in list" note already shows (D-12). The notice does not go on the CHECKS line. The reasons:
- The kept error can be about reviewers or review requests and not about checks (WR-05 case 1), so the notice describes the whole detail view.
- A separate line cannot be cut off at the end of a long CHECKS line in a narrow pane.
- "no checks" stays exactly "CHECKS  no checks".
The review offered "under the CHECKS line or the reviewers section" as examples. The note under the title meets its rule: a distinct faint notice that does not read as a run count.

Out of scope: IN-06 (ServerWait/NextDelay parity), IN-07 (help legend "unknown") and IN-01 to IN-05 stay open. WR-03 stays deferred. Do not touch `detailPage`, `classify`, `captureTransport`, `help.go` or the help goldens. Updating `03-REVIEW-DISPOSITION.md` (WR-05 to fixed) is the verify/review step's job, not this plan's.
