# Phase 03 Plan 09: The detail view never shows exact-looking counts on partial data (gap G-03-6-WR02)

## Phase Goal

**As a** prv user watching my pull requests, **I want to** see without leaving the terminal who and what is holding each PR up (which reviewers, which failing check, and whether it can merge), **so that** at a glance I can tell which watched PRs are approved, blocked, or failing CI.

<objective>
Close UAT gap G-03-6-WR02 (code-review finding WR-02, marked "fix before ship" by the user on 2026-10-12).

Today `FetchDetail` (internal/github/checks.go) keeps partial GraphQL data, skips null context nodes without counting them, and drops the signal that a page carried a GraphQL error. The detail view then shows counts such as "2 failing · 10 passing" with no "read N of M runs" note, and a failing check on a nulled node is invisible on the screen whose job is to show blockers.

- Task 1: a null context node makes `Read < Total`, and FetchDetail marks the result Truncated, so the screen says "read 1 of 2 runs". Proven end to end through the real client and the real ui.Model.
- Task 2: a page whose GraphQL error was kept marks the result Truncated even when every check node arrived (the error may have nulled a reviewer or a review request instead).

Purpose: the D-08 summary line must be honest about a partial read (D-03, D-08: "keep the exact counts and say how much was read"). The UI already renders "read N of M runs" whenever `Truncated` is set (TestDetailTruncatedSummary), so no UI code changes.
Output: two small changes in `FetchDetail` / `detailPage`, `TestFetchDetailPartial`, `TestDetailPartialEndToEnd`.

Out of scope: WR-03 (per-request rate-limit header capture, detail budget accounting) was DEFERRED by the user. Do not touch `captureTransport`, `classify(err, c.capture.latest())` or `wireDetailResp.RateLimit`. `fetchFailing` has a similar gap but already adds a warning; leave it alone.
</objective>

## Notes for the executor

- go-gh decodes `data` together with `errors[]` on an HTTP 200 and returns `*api.GraphQLError`; `classify` maps a non-rate-limit GraphQL error to `KindGraphQL` (proven by `TestFailingPartialErrors` with testdata/failing_partial.json). A realistic nulled node always comes with an errors[] entry, so the end-to-end body carries both.
- Each fix needs a test that fails before the fix and passes after it. Write the test first, run it, and confirm it fails for the expected reason (Truncated false, or the "read 1 of 2 runs" text missing) before you change checks.go.
- The UI shows "read N of M runs" also when Read == Total but a kept error made the read partial (for example "read 3 of 3 runs"). That is what the gap's truth asks for: the counts are marked as possibly incomplete whenever GitHub reported an error next to the data.
