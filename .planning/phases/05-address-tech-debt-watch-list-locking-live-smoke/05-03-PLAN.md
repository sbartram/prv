### Which assertions can drift (rule-sensitive and perishable fields)

| Field | Pins | Can drift? | How |
|-------|------|------------|-----|
| Review | 1-10 (every pin that has a Review) | yes, rule-sensitive | GitHub computes reviewDecision from the current branch rules and reviewer access (RESEARCH Pitfall 4, A2), in any direction: 1 and 8 none → required if a rule is added; 2, 3 and 9 approved → required if a rule gets stricter; 4 and 10 changes → required or approved if the requester's review stops counting; 5, 6 and 7 required → approved (or none) if the rule is removed |
| State | 4, 10 (closed) | yes | a maintainer can reopen a closed PR (Pitfall 2); merged pins cannot change |
| CI | 6, 7, 9, 10 (expected not CINone) | yes, perishable | GitHub drops old check data (Pitfall 3) |
| CI == CINone | 1-5, 8 | no | the data is already gone |
| Merge == MergeNone | 1-10 | no | DeriveMerge returns MergeNone for every merged or closed PR |
| Unavail NotFound | 11 | no | no PR can have the GraphQL Int maximum |

prv's Review is a pure function of the raw reviewDecision and the PR's review history (DeriveReview), and the review history of a merged or closed PR is fixed in practice. So a Review mismatch has one of two causes: GitHub recomputed reviewDecision (drift), or prv's mapping changed (a bug). The raw reviewDecision tells them apart. Because of that, no Review assertion is weakened or dropped: drift on any pin, in any direction, is a skip, and a prv mapping bug is still a failure.

Drift rules (each a `t.Skipf` on that pin's subtest only, with a message naming the pin and saying "re-pin (see the TestLive doc comment)"; all are evaluated before the first field assertion):
1. expected StateClosed, got StateOpen → "reopened on GitHub";
2. got Review != expected Review, and the raw reviewDecision now differs from the pin's recorded value → "reviewDecision is now X (was Y on 2026-10-13), so the repository's review rule or a reviewer's access changed" (X and Y print `null` for `""`). When the raw value is unchanged, the mismatch is a `t.Errorf`: "Review = GOT, want WANT (reviewDecision is still Y, so prv's mapping changed)". When the raw query fails, the mismatch is a `t.Errorf` that says the raw reviewDecision could not be read;
3. expected CI is not CINone, got CINone → "GitHub expired the check data".

## Flagged assumptions and choices (carried, not silently dropped)

- **Perishable data (RESEARCH A1, A2):** GitHub appears to drop check data after about 400 days and computes `reviewDecision` from the current branch rules. The drift rules make both a skip with a re-pin message, so a GitHub-side change is never reported as a prv bug.
- **Review drift is symmetric (Claude's discretion under D-13, revision 2):** every Review assertion is rule-sensitive (table "Which assertions can drift"). On a Review mismatch the test reads the raw `reviewDecision` of that one pin with a direct read-only GraphQL query (go-gh `api`, the same token, `LogIgnoreEnv: true`) and compares it with the value recorded on 2026-10-13. A changed raw value is a skip in any direction; an unchanged one is a failure. This keeps the review assertions able to catch a prv mapping bug, which a rule such as "skip any mismatch that involves required" could not do. The query runs only on a mismatch, so a normal run still costs about 4 points. Residual risk, accepted: if someone dismisses a review on a merged PR whose raw value is null, the result is a failure whose message says the raw value is unchanged, so the developer checks the reviews on github.com.
- **Env var and placement (Claude's discretion):** `PRV_LIVE=1`; `internal/github/live_test.go` in the external package `github_test`, so it uses only the exported API, like a real caller.
- **Live verify in this plan:** the executor runs the live command once (network and a gh login are available here per RESEARCH Environment Availability). It costs about 4 points of the 5,000/h budget.
- **The low-budget warning check (test 2, user decision 2026-10-13, "Test-only render"):** a live low budget needs about 4,000 points spent, so the user chose an opt-in, test-only render path with no product code change. `TestShowRateWarning` (`internal/ui/show_test.go`, skipped unless `PRV_SHOW=1`, the same style as `PRV_LIVE`) builds the real model with a budget of 999 of 5000 and prints the real list screen, ANSI kept, at 80 and 40 columns.
