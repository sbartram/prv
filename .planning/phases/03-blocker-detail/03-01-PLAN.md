# Phase 03 Plan 01: Tracer — a failing PR's row names the check that is failing

## Phase Goal

**As a** prv user watching my pull requests, **I want to** see without leaving the terminal who and what is holding each PR up (which reviewers, which failing check, and whether it can merge), **so that** at a glance I can tell which watched PRs are approved, blocked, or failing CI.

(The capability comes from the ROADMAP Phase 3 Goal line and the outcome from the PROJECT.md Core Value. The ROADMAP Goal line is not written in user-story form; see the planner's return note.)

<objective>
Prove the D-01 two-step fetch end to end first, then name every kind of failing check correctly.

- Task 1 (tracer): discovery → FailingChecks `nodes(ids:)` query for the failing PRs → `domain.ClassifyCheck` / `LatestChecks` / `SummarizeFailing` → `PR.Failing` → CI cell `✗ lint +2`, proven by an end-to-end test through the real `github.Client` and `ui.Model`. The one path: GitHub Actions check runs that fail or pass.
- Task 2: every other kind of check is classified and named right (D-02, D-03, D-04): status contexts such as Jenkins, timed-out and startup failures, cancelled-only PRs, skipped and neutral runs, unknown values; hostile names are cleaned.

Purpose: success criterion 2 ("the row for a PR with failing CI names one of its failing checks"). Decisions D-01, D-02 (revised), D-03, D-04 and the "never guess a name" discretion item. Roadmap pitfalls: the list badge always comes from the rollup state, re-runs are not double-counted. Plan 03-02 then proves the same path on messy real data (re-run fixture, truncated pages, partial errors, many failing PRs, rate limits, long names).
Output: `internal/domain/checks.go`, `internal/github/checks.go`, `internal/ui/cells.go`, routed fixture transports, `failing_contexts.json`, and tests.
</objective>

## Flagged assumptions (carried, not silently dropped)

- RESEARCH A3: chunks of 25 ids are based on one measurement (30 PRs, 2.9 s). There is no cap on how many failing PRs are named per refresh: D-01 says to chunk when more than 100 PRs fail, and LIST-07 asks for a name on every failing row. Discovery already lists at most 500 PRs (maxPages 5), so one refresh sends at most 20 FailingChecks requests (1 point each). A refresh with hundreds of failing PRs is slower; the Phase 2 backoff protects the rate limit.
- RESEARCH A4: duplicates were only seen across check suites; the (kind, workflow, name) key handles both cases.
- The FailingChecks text from RESEARCH has not been run exactly as written. Task 1 step 10 runs it once read-only; if `gh` is not logged in, the SUMMARY records "not validated live".
- '+N' (D-02 says "how many more fail"; D-04 names a cancelled check only when nothing fails): '+N' counts the other failing checks when a failing check is named, and the other cancelled checks when the named check is cancelled. A cancelled check is never added to a failing count, so "✗ lint +1" matches a detail summary of "2 failing · 1 cancelled".
- The named check is the first failing one by case-insensitive name, so the row text does not change between refreshes. CONTEXT does not fix which failing check is named.
- LIST-07 v1 limit (user-accepted, revised D-02): a failing PR whose contexts need more than one 100-context page shows the plain badge. Recorded under LIST-07 in REQUIREMENTS.md and against ROADMAP success criterion 2.
- Edge-probe rows DETL-03 and NAV-05 are unclassified; they are carried as flagged assumptions in plans 03-03 and 03-08.
