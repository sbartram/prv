# Phase 02 Plan 06: prv backs off by itself when the budget is short or a limit is hit, says until when, and refuses r during the pause

## Phase Goal

**As a** developer who keeps prv open in a terminal pane all day, **I want to** have it refresh itself, stay inside the API rate limit, narrow the list and jump to a PR on github.com, **so that** I can trust that what I see is current without opening a browser.

<objective>
- Task 1: a pure `domain.NextDelay` decides every delay: retry-after, then resetAt, then bounded exponential, plus a reserve pause and pacing when the budget is short.
- Task 2: the model applies it after every result, pauses, refuses `r` during a pause with a message (D-08), keeps retrying a failed first fetch on that schedule (D-09), and a simulated hour proves the call counts, gaps and pauses.

Purpose: the "backs off on its own and shows when it will resume" part of success criterion 2. Decisions D-08, D-09. Roadmap pitfalls: backoff order retry-after → resetAt → bounded exponential; verify with a counting fake over a simulated hour. Plan 02-07 feeds real GitHub rate-limit responses into this policy.
Output: `internal/domain/backoff.go`, pause state, the refusal flash and the paused header in `internal/ui`, `internal/ui/ratelimit_test.go`.
</objective>

## Flagged assumptions (carried, not silently dropped)

- RESEARCH A2: thresholds are tunables, not facts: reserve = 10 × max(cost, 1), failure base max(interval, 30 s), failure cap max(5 min, interval), server-delay clamp [1 s, 65 min], 60 s floor for a rate limit with no timing. - Until plan 02-07 lands, only test doubles carry Backoff(); real GitHub errors take the plain-failure path (rule c). The reserve pause and pacing (rule d) already work on real responses because they read the rateLimit data from 02-05.

1. internal/domain/backoff.go (new, pure: the current time is always the now parameter, never read from the clock): type Outcome struct { Failed, RateLimited bool; RetryAfter time.Duration; ResetAt time.Time }. type Delay struct { Wait time.Duration; PausedUntil time.Time }. Exported constants MinServerWait = time.Second, MaxServerWait = 65 * time.Minute, MinFailureBase = 30 * time.Second, MaxFailureWait = 5 * time.Minute, RateLimitFloor = time.Minute, ReservePerCost = 10. func NextDelay(now time.Time, interval time.Duration, failures int, rl RateLimit, last Outcome) Delay, applying the rules in this order (interval below one second is treated as one second):
   (a) last.Failed and last.RetryAfter > 0 → Wait = clamp(RetryAfter, MinServerWait, MaxServerWait), PausedUntil = now+Wait.
   (b) last.Failed and last.RateLimited → reset = last.ResetAt when it is after now, else rl.ResetAt when it is after now; with a reset, Wait = clamp(reset.Sub(now)+time.Second, MinServerWait, MaxServerWait); without one, Wait = max(RateLimitFloor, the exponential of rule c); PausedUntil = now+Wait either way.
   (c) last.Failed → base = max(interval, MinFailureBase); Wait = base doubled (failures−1) times, stopping as soon as it reaches capWait = max(MaxFailureWait, interval), then min(Wait, capWait) — a loop that stops at the cap, never a bare shift, so 1000 failures cannot overflow. No pause: r stays allowed (D-09).
   (d) success → Wait = interval. When rl.Limit > 0 and rl.ResetAt is after now: cost = max(rl.Cost, 1); when rl.Remaining <= ReservePerCost*cost → Wait = clamp(rl.ResetAt.Sub(now)+time.Second, MinServerWait, MaxServerWait) and PausedUntil = now+Wait; otherwise left = rl.Remaining / cost and when int64(rl.ResetAt.Sub(now)/interval) > int64(left) set Wait = max(interval, rl.ResetAt.Sub(now)/time.Duration(left)) (division only, no multiplication of durations). No pause for pacing.
   The yellow display threshold of plan 02-05 stays separate (pure display).
