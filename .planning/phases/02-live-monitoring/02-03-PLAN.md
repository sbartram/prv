# Phase 02 Plan 03: The PRs that need attention come first, the order holds still between refreshes, and the selection follows the PR

## Phase Goal

**As a** developer who keeps prv open in a terminal pane all day, **I want to** have it refresh itself, stay inside the API rate limit, narrow the list and jump to a PR on github.com, **so that** I can trust that what I see is current without opening a browser.

<objective>
- Task 1: rows come back from GitHub in attention order — failing CI and changes requested first — with keys that polling does not change (D-01, D-02, D-04). The query gains `createdAt`.
- Task 2: the selected PR stays selected across refreshes even when it moves, with a nearest-neighbour fallback when it leaves the list (D-03, RFSH-06).

Purpose: success criterion 3. Roadmap pitfalls: selection tracked by PR ref, nearest-neighbour fallback; stable sort on a key polling does not change.
Output: `domain.Bucket`, new `domain.Sort`, `PR.CreatedAt`, `rebuild()` with selection by ref, `internal/ui/selection_test.go`.
</objective>

<assumption_delta_decision>
- Detector: `assumption-delta scan 2` fired a pluralization signal on "nearest-neighbour fallback" (selection).
- Primary noun now: `domain.Ref` (owner/repo#n) is the identity of the selection. The row index (`cursor`) is demoted to a value derived from `selected` on every rebuild.
- Decision: promote. The Phase 1 model kept only `cursor` (an index); this plan makes `selected domain.Ref` the source of truth and recomputes `cursor` from it, instead of keeping both as independent state.
- Invariant test (accepted): TestSelectionInvariant — after any sequence of refresh results and j/k presses, whenever the selected ref is in the visible rows, `rows[cursor].Ref == selected`.
</assumption_delta_decision>
