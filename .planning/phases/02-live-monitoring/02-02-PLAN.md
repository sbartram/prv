# Phase 02 Plan 02: prv shows how much API budget is left and backs off by itself when the limit is low or used up

## Phase Goal

**As a** developer who keeps prv open in a terminal pane all day, **I want to** have it refresh itself, stay inside the API rate limit, narrow the list and jump to a PR on github.com, **so that** I can trust that what I see is current without opening a browser.

<objective>
Make the long-running session safe for the user's shared token.

- Task 1: the remaining API budget is always visible (faint `api N` in the footer) and turns into a yellow header warning below 20% (D-06). The query gains `limit`.
- Task 2: a pure `domain.NextDelay` decides every delay (retry-after, then resetAt, then bounded exponential, plus pacing when budget is short). The model applies it after every result, pauses, refuses `r` during a pause with a message (D-08), and keeps retrying a failed first fetch on that schedule (D-09). A simulated hour proves it.
- Task 3: real GitHub rate-limit responses drive it: a header-capturing transport and `KindRateLimited` with `Backoff()` cover the HTTP-200 primary limit and the 403/429 secondary limit.

Purpose: success criterion 2 (rate limit shown, automatic backoff, shows when it resumes). Decisions D-06, D-08, D-09. Roadmap pitfalls: backoff order retry-after → resetAt → bounded exponential; every query carries rateLimit; verify with a counting fake over a simulated hour.
Output: `internal/domain/backoff.go`, `internal/github/ratelimit.go`, rate-limit classification, `api N` footer, header warnings, `internal/ui/ratelimit_test.go`.
</objective>

## Flagged assumptions (carried, not silently dropped)

- RESEARCH A1: GitHub's primary-limit GraphQL error carries `type: "RATE_LIMITED"`. It is a second signal only; the documented `x-ratelimit-remaining: 0` header is the first.
- RESEARCH A2: thresholds are tunables, not facts: reserve = 10 × max(cost, 1), failure base max(interval, 30 s), failure cap max(5 min, interval), server-delay clamp [1 s, 65 min], 60 s floor for a rate limit with no timing. Wrong values cost latency, not correctness. The cap max(5 min, interval) is a planner choice so a failure never retries faster than a long configured interval allows.
- RESEARCH A7: `Retry-After` is read as whole seconds; an HTTP-date value is treated as absent and the reset or exponential rule applies.
- Transient messages (the D-08 refusal) stay about 4 s (RESEARCH A10, Claude's discretion). They clear through a redraw message armed with the same injectable timer, so the simulated clock controls them in tests.
