# Phase 01 Plan 02: The right PRs, once each, in a stable order — with honest loading, failure and empty states

## Phase Goal

**As a** prv user who watches my own GitHub pull requests, **I want to** run `prv` and see, from live GitHub data, every PR I authored or am assigned to with its state, review status and CI badge, **so that** I can tell which are approved, blocked or failing CI without opening a browser.

<objective>
Make the list trustworthy. Task 1: the list holds exactly the authored and assigned PRs inside the closed window, each once, across up to five pages, in the D-06 order. Task 2: launch, failure and empty states tell the user what is happening and how to fix it (spinner, error panel with hint and `r` retry, empty state that names the account, partial-data and truncation notes), and the token never appears in any of them.

Purpose: success criteria 1 and 2 (live data, no duplicates, 14-day window, clear failure messages) and D-06, D-08, D-09, D-10.
Output: `internal/domain/list.go`, `internal/github/errors.go`, paged `Fetch`, a full ui state machine, fixture and state tests.
</objective>

## Flagged assumptions (carried, not silently dropped)

- WATCH-03 (edge unclassified by the probe): the planner's truths cover duplicates by node id, on one page and across pages. A PR that GitHub returns under two different node ids is not handled (never observed).
- AUTH-03 (edge unclassified by the probe): coverage is TestTokenNeverAppears over every error path plus the static greps in 01-04. Phase 1 has no log file, so there is no log path to check.
- RESEARCH A1: search may silently omit PRs from organizations whose SSO has not authorized the token, and the FORBIDDEN shape was not observed (no SAML org on the account). prv shows partial-data warnings when GitHub reports errors, but cannot detect a silent omission.
- RESEARCH A2: `closed:>=DATE` is date-granular in an unknown zone; neutralised by the one-day query margin (01-01) plus the exact `InWindow` filter (this plan).
- WATCH-02 live assigned PRs: backstop truth above (stand-in evidence only).

## Known limits (accepted for Phase 1)

- Open-PR completeness cap: `maxPages = 5` with `first: 100` reads at most 500 search results, at cost 1 per page (RESEARCH Pattern 3). Success criterion 2 asks for every open PR; an account with more than 500 matching PRs gets the 500 most recently updated, because the search sorts by update time. The cap is disclosed, not silent: Fetch sets `Snapshot.Truncated` (TestTruncatedAfterFivePages) and the list footer shows "list truncated" (TestFooterNotes). For scale, the user's account has 15 PRs in total, and GitHub search returns at most 1,000 results for any query. The cap stays at 5 pages in Phase 1. The user accepted this cap explicitly; the acceptance is recorded in 01-CONTEXT.md "Plan-time decisions" (the 500-result entry).
